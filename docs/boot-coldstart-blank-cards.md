# 冷启动后翻牌卡片空白（时间显示不全）

## 1. 现象

开机自启动后，主界面的时间随机缺块：刚进桌面只有秒卡，约一分钟后出现分+秒，
小时卡要到整点才亮起来。同一现象也能在「灭屏状态下拉起应用」时复现，
并非开机特有。

## 2. 根因

时间卡片的内容（底板 + 数字 + 分割线）是一次性烘焙进 GPU 纹理的，只有在这个
位上的数字发生变化、或卡片尺寸变化时才会重画（`card.c` 里的 `should_redraw`）。

冷启动时，后台启动 Activity 的限制与锁屏会把界面推过一条
`pause → stop → surfaceDestroyed → 重启 → resume` 的路径。SDL 在这条路径上
重建 EGL 上下文，并通过窗口事件通知应用「渲染目标已经没了」。此时应用自己
烘焙的全部纹理都失效，但主循环里没有任何一处响应这个通知：

- 处理窗口恢复的分支里，重画调用原本是被注释掉的，旁边留着
  `XXX: It seems OK without redrawing` 的说明；
- Windows 分支里的同类事件只用来退出屏保预览。

于是纹理空白一直保留到该位数字下次变化为止。秒每秒变，所以 1 秒内自愈；分最长
60 秒；时最长接近 1 小时。这与现场观察到的「先只亮秒、一分钟后亮分和秒、小时
仍缺」完全对应。

信息栏与顶部日期带每帧都重新生成纹理，天气在文字变化时重画，因此日期、星期、
农历看起来是正常的——缺的只有翻牌卡片。

## 3. 修复

在两个通知点上都做同一件事：销毁旧纹理、按当前数字重新烘焙、请求重画，并让
天气文字重新标记为脏。

- `clock.c`：窗口恢复分支改为调用新增的 `flipclock_clock_reset_textures()`，
  该函数先解绑渲染目标（不能销毁仍绑定为 target 的纹理），再逐张重置时/分/秒卡。
- `card.c`：新增 `flipclock_card_reset_textures()`，重建纹理、清掉半程翻牌状态
  （否则会对着空白纹理做动画）并置 `should_redraw`。
- `flipclock.c`：把 `SDL_RENDER_TARGETS_RESET` 与 `SDL_RENDER_DEVICE_RESET`
  合并处理，Windows 屏保预览保持原有的「直接退出」逻辑，其余平台走重建。

## 4. 验证

指标：截图里能数出的卡片底板数量（背景纯黑、底板 (32,32,32)，分割线是背景色，
所以一张卡会分成上下两块，按横向重叠归并）。完整 = 3。

同一套灭屏冷启动流程（强杀 → 灭屏 → 拉起 → 等 6 秒 → 亮屏 → 截图）跑 10 轮：

| 版本 | 3 张卡 | 只有 2 张（缺小时） | 只有 1 张（只剩秒） |
| --- | --- | --- | --- |
| 去掉修复（对照） | 3 | 2 | 5 |
| 带修复 | 10 | 0 | 0 |

对照组失败的形态与用户报告的现场完全一致，说明该流程有区分力，修复针对的就是
同一条路径。设备上每次拉起都会打出「窗口恢复」日志，即修复后的分支被 10/10 命中。

归因修正：这台机器上 30 轮里「渲染设备/目标被重置」那条通知一次都没有出现，
真正每次都触发的是窗口恢复事件。也就是说生效的是窗口恢复那条路径，
另一条属于防御性覆盖，本机型上没有实测证据。

## 5. 遗留

- 「重画失败就重试」的兜底暂未实现：当前做法是在收到通知时主动重建，没有校验
  重建是否真的成功。
- 天气纹理缓存与卡片是同一类失效模式，本轮只靠「标记为脏、下帧重画」覆盖，
  未做额外校验。
- 真机开机链路的端到端复验仍未做：卸载重装会重置悬浮窗授权与电池优化豁免，
  本次已用命令行重新授予，但重启设备走一遍自启的路径还没有跑。
